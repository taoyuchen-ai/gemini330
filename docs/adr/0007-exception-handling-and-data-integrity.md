# ADR-0007: 系统异常处理与数据完整性

- **Status**: Accepted
- **Date**: 2026-10-01

## Context

课堂长时运行 8 周（基线 2 周 + 干预 4 周 + 跟踪 2 周），可能遇到：

- Gemini335 USB 断开或 SDK 崩溃
- 被试离座（上厕所、被叫走）
- Dotii-Display HTTP API 失联（管理中心进程崩溃）
- 主机崩溃（Windows 蓝屏/断电）
- MediaPipe 单帧推理超时

需要明确每类异常的处理策略与数据完整性保证。

## Decision

| 异常 | 处理策略 |
|---|---|
| 相机掉线 | 自动重连 3 次（每次间隔 5 秒）→ 仍失败标记 timestamp 起数据为缺失 → 触发 PI 短信/邮件报警 |
| 被试离座 | 连续 30 秒检测不到骨架 → 标记"离座"状态，不计入坐姿统计；返回后自动恢复 |
| Dotii API 失联 | 1 秒超时重试 1 次 → 仍失败写日志、不阻塞姿态检测；连续 5 次失败触发 PI 报警 |
| 主机崩溃 | 每分钟落盘当前会话坐标到 SQLite（WAL 模式），崩溃后恢复到上一分钟 |
| MediaPipe 单帧超时 | 跳过该帧，统计时按缺失处理（按 ADR-0006 不计入分母） |

**数据完整性保证**：

- 原始坐标每分钟落盘到 SQLite，WAL 模式支持崩溃恢复
- 缺失帧按剔除处理，不插值
- 缺失比例 > 20% 的会话整体剔除不入分析
- 异常日志独立存储，供报告"系统可靠性"章节使用

## Consequences

- 数据缺失在统计时按"剔除"处理，可能引入选择性偏差（缺失多发生在某些条件下）——需在报告讨论中说明
- PI 报警机制需配置短信/邮件通道（如阿里云短信服务或企业微信机器人）
- SQLite 落盘增加 IO，但 30 fps × 6 人小数据可承受（峰值 ~10 MB/分钟）
- 报告需报告"系统可用性"指标（有效采集时长 / 计划采集时长），透明披露数据完整性
- 崩溃恢复到上一分钟意味着最多丢失 1 分钟数据，可接受
